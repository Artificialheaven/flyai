# 会话传输与带宽优化方案

- 文档日期：2026-11-23
- 关联文档：`docs/性能与CPU热点排查报告.md`
- 范围：会话存储格式、`/api/sessions/*` 接口、前端会话缓存、静态压缩
- 状态：**设计稿，未实施**

---

## 0. TL;DR

SillyTavern 的 `/api/chats/get|save` 也是「全量」传输，没有增量接口（ST 1.19.1 的 `/api/chats` 共 13 条路由，见 `docs/SillyTavern服务端接口清单.md`）。但 ST 的 chat 文件只存对话文本：角色卡、世界书、图片都在独立文件里，所以全量通常只有几十到几百 KB。

FlyAI 的会话文件之所以能到 11–30MB，是因为**同一张卡在会话里存了两份**（`character_override` 与 `members[].override` 完全相等），卡内 `regex_scripts` 又与 `extensions.regex_scripts` 完全相等；旧文件还内嵌了 `tavern_helper` 脚本（这部分现在落盘时已剥离）。

本方案分四层，按收益/成本排序：

| 阶段 | 内容 | 预计收益 |
|---|---|---|
| L1 | 会话数据去重（卡只存一份、世界书按引用） | 示例会话 11.6MB → ≈3.7MB（稳态）；响应体同步缩小 |
| L2 | 卡包 / 作者脚本按 digest 单独下发并缓存 | 每次打开会话少传 1–5MB |
| L3 | HTTP 条件请求（ETag/304）+ 消息增量同步 | 稳态打开 **0 字节**；每条消息只传新增 KB |
| L4 | 图片外置、压缩策略、前端增量落盘 | 消息体不含 base64；CPU 与带宽双降 |

> 全部改造保持 ST 卡沙箱/作者运行时的兼容语义不变；`/api/sessions/*` 是自有协议，可直接演进。

---

## 1. 目标与非目标

### 1.1 目标

1. 单会话稳态存储体积降到「卡的一份副本 + 对话」量级；
2. 打开已缓存的会话时，服务端与客户端都尽量不重复处理大对象；
3. 新增一条消息时，网络传输只包含该消息本身，不重复传输卡与历史；
4. 保持旧会话文件、旧 APK 客户端可继续使用（渐进迁移，可回滚）；
5. 不改变提示词组装、压缩、导出、发布等业务语义。

### 1.2 非目标

1. 不引入数据库替换 JSON 存储（本轮先做格式与接口优化）；
2. 不改变 ST 卡沙箱的 API 形状（`/api/st/*`、作者运行时 shim 保持现状）；
3. 不追求 `/api/chats/*` 的 ST 路径级兼容（如未来要做，按第 7 节适配）；
4. 不优化消息文本本身的压缩率（gzip/brotli 已覆盖）。

## 2. 现状与瓶颈数据

### 2.1 已存在的优化

代码里已经有一层「重字段剥离」：

- `flyai/sessions/resolve.py:31 strip_heavy_extensions`：去掉 `extensions.tavern_helper` / `TavernHelper`；
- 落盘：`flyai/sessions/json_store.py:120`（成员 override）、`:136`（会话级 override）；
- 下发：`flyai/api/routes_session.py:1666 _member_dict_for_client`、`:1673 _session_dict` 内的 `_strip_heavy_extensions`；
- 读取时从库主卡补回：`flyai/sessions/resolve.py:46 _restore_heavy_extensions`。

所以旧文件重存后会从 30.5MB 缩到约 11.6MB。**这是已经修掉的部分，本方案不再重复。**

### 2.2 仍然存在的重复（实测）

一个 9 条消息的会话（重建后 11.6MB）：

```
messages（9 条）              0.047 MB
character_override            4.59 MB
  table[]                     2.70 MB
  regex_scripts[]             0.94 MB
  extensions.regex_scripts[]  0.94 MB   ← 与顶层 regex_scripts 完全相等
members[1].override           4.59 MB   ← 与 character_override 完全相等
world_override                2.70 MB   ← 即使未修改也全量保存
```

产生位置：

- `flyai/api/routes_session.py:985-989`：写成员 override 后 `s.character_override = copy.deepcopy(m.override)`，主动镜像出第二份；
- `flyai/lore/card_import.py:168-212`：导入时把 `extensions.regex_scripts` 复制到顶层 `regex_scripts`，但 `extensions` 里的原字段保留；
- `flyai/sessions/resolve.py:134 set_world_override`：世界书整体 `to_dict()` 存入会话。

### 2.3 下发与客户端

- `GET /api/sessions/{sid}` 每次返回 `members[].override` + `character` + `st`（含作者脚本，最大 5MB）+ `world`；
- 客户端每轮 `done` 后 `refreshSession` 整会话重拉（`webapp/src/services/chat/store.ts:2568`）；
- 每次落盘整会话写 IndexedDB（`webapp/src/services/chat/db.ts:84`）；
- GZip L9 全量压缩（`flyai/app.py:613`），见审计报告第 3 节。

## 3. 设计原则

1. **单一事实来源**：同一份内容在磁盘和响应里只出现一次；
2. **引用优先于拷贝**：世界书、库卡、作者脚本能按 `id + digest` 引用就不复制；
3. **读时重建**：磁盘格式可以精简，内存对象保持现有形状，避免大面积改业务代码；
4. **向后兼容**：旧文件可读、旧客户端可用；新客户端按能力协商；
5. **可度量**：每个阶段给出体积/耗时指标与验收用例；
6. **先做便宜且确定的**：去重 > 条件请求 > 增量接口 > 图片外置。

---

## 4. 目标数据流

```
打开会话：
  客户端(本地缓存) ──ETag/rev──> 服务端
        │                          │ 304（未变化）或 200（meta + 增量消息）
        └────────── 合并渲染 ──────┘
  卡/作者脚本：GET /sessions/{sid}/card-bundle?digest=...（immutable 缓存）

发送消息：
  POST /api/chat（SSE，已是增量事件）
    → 服务端只读写「变更部分」：追加消息 + 消息级持久化
    → done 后客户端用 ?after=<index> 拿新增消息（而不是整会话）
```

## 5. L1：会话数据去重（P0）

### 5.1 单 AI 会话：override 只存一份

#### 现状

- `RoomMember.override` 是「会话副本的真实载体」；
- `session.character_override` 是兼容镜像（导出/压缩/`effective_character` 读顶层）；
- 两者在单 AI 会话里内容完全相同。

#### 目标格式

磁盘上**只保留 `members[].override`**，`character_override` 不再落盘：

```jsonc
// 单 AI 会话
{
  "character_id": "abc123",
  "character_override": null,          // 不落盘
  "members": [
    { "id": "u1", "is_user": true,  "override": null },
    { "id": "a1", "is_user": false, "override": { ...卡... } }
  ]
}
```

读取时重建（内存形状不变）：

```python
# flyai/sessions/json_store.py: session_from_dict
if not data.get("character_override"):
    ai_seats = [m for m in members if not m.is_user and m.override]
    if len(ai_seats) == 1:
        session.character_override = ai_seats[0].override   # 共享同一对象，不深拷贝
```

要点：

- **不要**在两个对象之间做「双向可写」共享；业务代码里所有写路径都是**整体赋值**（`m.override = ...`、`set_character_override(...)`），因此共享读引用是可接受的；
- 若担心未来出现原地修改，读取时可以用 `copy.deepcopy` 只重建顶层一份（内存成本换安全），但落盘仍然只有一份；
- `save_merged`（`flyai/sessions/store.py:37`）会先 `get()`，而 `get()` 已重建顶层，所以 `MERGED_FIELDS` 里的 `character_override` 合并行为不变。

群聊房间保持现状：每个 AI 座位可能有不同卡，`character_override` 不镜像（`flyai/api/routes_room.py:322-334` 已有该规则）。

#### 兼容性检查清单

| 场景 | 处理 |
|---|---|
| 旧文件（两份都在） | 直接可读；下次保存自动转为单份 |
| 旧代码读新文件 | 只可能出现在回滚时；需保证本方案上线后再回滚时，旧代码能从成员 override 恢复顶层的补丁一并发布（见 8.3） |
| 导出 / 压缩 / 发布 | 读的是内存对象，已重建，不受影响 |
| `is_character_scoped` | 读内存对象，不受影响 |
| 群聊 | 不改 |

### 5.2 卡内 `regex_scripts` 去重

`extensions.regex_scripts`（CCv3 导入来源）与顶层 `regex_scripts` 完全相同。目标：

- **落盘/下发时**：若两者 `==`，移除 `extensions.regex_scripts`；
- **读取时**：若顶层为空且扩展里有，则补到顶层（保持 `Character.regex_scripts` 唯一使用面）；
- **导入/导出时**：导出（`to_dict` 用于 ST 格式）按需还原 `extensions.regex_scripts`，保证酒馆卡导出保真。

实现位置建议：

- `flyai/lore/models.py` `Character.to_dict()`：增加 `strip_duplicate_extensions: bool = True` 参数（默认开启）；导出路径显式传 `False`；
- `Character.from_dict()`：读取时补回。
- 注意：`flyai/lore/card_import.py:168` 只用于导入解析，不改。

> 这一项同时作用于**角色库文件**与**会话副本**，收益是全局的（每张卡省约 0.9MB）。

### 5.3 世界书按引用

`world_override` 只有两种状态：

1. **未修改**：会话只需 `world_id` + `world_digest`；
2. **已修改**（压缩提案、卡内写回等）：保存完整副本。

判定方式：

- `set_world_override` 时记录来源 `world_id` 与当时 `world_digest`；
- 落盘时若 `world_override` 与库中同 digest 的世界书 `==`，则不存 override，改存 `world_override_ref: {"id": ..., "digest": ...}`；
- 读取时按 digest 从库中取；取不到（世界书被删/改）则回退为空并记录告警。

简化版（可先做）：只在 `world_override` 与 `lore.get_world(world_id).to_dict()` **完全相等**时丢弃 override。示例会话中世界书未被修改，预计省 2.7MB。

### 5.4 响应层去重

`GET /api/sessions/{sid}`：

1. 单 AI 会话：
   - 保留 `d["character"]`（已剥离重字段）；
   - `members[].override` 置为 `null`，改为轻量 stub：
     ```json
     "override_stub": { "name": "约会大作战P-v1", "avatar": "/uploads/..." }
     ```
   - 前端现有代码优先读 `detail.character`（`webapp/src/services/chat/store.ts:728`），并可用 stub 显示名字/头像（`RoomMembersDialog.tsx:98-102` 改为 `member.override_stub ?? member.override ?? chair`）。
2. 群聊：保留各成员 override（卡通常不同），但对每个成员同样做 5.2 的字段去重。
3. `st.author.scripts` 改为按 digest 下发（见 L2）。

### 5.5 L1 收益

| 项目 | 现状 | L1 后 |
|---|---|---|
| 会话文件 | 11.6MB | ≈3.7MB（卡 3.65MB + 消息 47KB；世界书按引用） |
| GET 响应 | 约 10MB+ | ≈3.7MB |
| 旧文件（30.5MB） | 重存即收敛到 3.7MB | 同上 |

## 6. L2：卡包与作者脚本按 digest 下发

### 6.1 问题

`_st_payload`（`flyai/api/routes_session.py:1494` 附近）每次打开会话都内联 `st.author.scripts`（上限 5MB），即使内容完全没变。卡内脚本绝大多数是静态的。

### 6.2 方案

新增接口：

```
GET /api/sessions/{sid}/card-bundle?digest=<md5>
→ 200 { "digest": "...", "author_scripts": [...], "panels": [...], "truncated": false }
→ 304（If-None-Match 命中）
```

- `digest` 复用 `LoreStore.character_digest`（`flyai/lore/store.py:137`，已有按 stat 缓存的 md5）；
- 响应头：`Cache-Control: private, max-age=31536000, immutable`（digest 变化即 URL 变化）；
- `_st_payload` 里只保留 `author.scripts_digest` 与 `author.scripts_url`；
- 客户端首次打开拉一次，之后从 IndexedDB/localStorage 取；
- 旧 APK 兼容：请求头不带 `X-FlyAI-Client >= 2` 时仍内联（灰度期默认内联，稳定后切换）。

### 6.3 收益

每次打开会话少传 1–5MB；服务端少一次 `collect_author_scripts` 深拷贝。

## 7. L3：HTTP 条件请求与增量消息

### 7.1 ETag / 304

`GET /api/sessions/{sid}`：

- 在**解析文件之前**计算弱 ETag：
  ```
  W/"sess-<mtime_ns>-<size>-<cfg_rev>-<settings_mtime_ns>-<server_ver>"
  ```
  - `mtime_ns/size` 来自 `Path.stat()`（新增 `SessionStore.stat(sid)`）；
  - `cfg_rev` / `settings_mtime_ns` 覆盖「配置或用户设置变了，但会话文件没变」的情况（`st` 段依赖它们）；
- 客户端带 `If-None-Match`；命中直接 `304`，**不读文件、不解析、不序列化、不压缩**；
- 这是同时省带宽和 CPU 的关键：传输 0 字节，服务端只做几次 stat。

注意：gzip 中间件对 304 不产生 body，无额外 CPU。

### 7.2 增量消息同步

#### 接口

```
GET /api/sessions/{sid}/sync?thread_id=<tid>&after=<index>
→ 200 {
    "rev": "<thread-rev>",
    "reset": false,
    "total": 128,
    "messages": [ ...索引 >= after 的消息... ]
  }
→ reset=true 时附带最近 N 条 + 完整元数据（编辑/删除/分支切换等无法增量时）
```

- `index` 是该线程内的消息下标（现有模型没有持久化 `seq`，先用 index，避免改消息 schema）；
- `after = 客户端已有条数`；
- 服务端只需 `get()` 后切片序列化，不回传历史前缀；
- 会话元数据（标题/成员/设置）走单独的 `GET /api/sessions/{sid}/meta`（小对象），或在 `sync` 里以 `meta_changed` 标记。

#### 何时 reset

- 消息被编辑/重新生成/撤回/删除/切换分支 → 前缀被替换；
- 线程切换；
- `after` 超出 `total`；
- 旧客户端不支持 sync → 仍走全量 GET。

#### 客户端合并

- `store.ts` 在 `done` 后改调 `sync`：拿新增消息 + `meta_changed` 时才拉 meta；
- 若 `reset=true` 再回退全量 `GET /sessions/{sid}`；
- SSE 流式事件保持现状（已是增量 + 断线续读）。

### 7.3 分页

首屏只取最近 50 条：

```
GET /api/sessions/{sid}/messages?thread_id=<tid>&before=<index>&limit=50
```

- 向上滚动时加载更早的消息；
- 新消息继续走 `sync?after=`；
- 前端消息列表在 >200 条时启用虚拟滚动（可放 L4）。

### 7.4 收益

| 操作 | 现状 | 目标 |
|---|---|---|
| 打开未变化的会话 | 全量 10MB+ / 1–2s | 304，0 字节 |
| 新增一条消息后同步 | 全量会话 | 新增消息 + 少量元数据（KB 级） |
| 首屏打开长会话 | 全部历史 | 最近 50 条 |

## 8. L4：图片外置、压缩与前端

### 8.1 图片外置

当前 `ImageAttachment`（`flyai/schemas.py:39`）是 `{media_type, data(base64)}`，用户上传图直接内联进会话文件与响应。

目标：

```jsonc
// 新格式（向后兼容）
{
  "media_type": "image/webp",
  "url": "/uploads/<uid>/<sha256>.webp",
  "thumb_url": "/uploads/<uid>/<sha256>.thumb.webp",
  "sha256": "...",
  "w": 1280, "h": 720,
  "data": ""            // 新数据不再填充；旧数据保留
}
```

- 上传时即落盘 + 生成缩略图（可用现有 `/uploads` 静态目录）；
- 前端优先 `url`，没有 `url` 时回退 `data`；
- 旧会话读取时**懒迁移**：第一次读到 `data` 时写文件并替换为 `url`（只写一次）；
- 旧 APK 兼容：按客户端版本决定响应里是否附带 `data`（灰度期可附带）；
- 模型视觉输入仍在服务端从文件/base64 组装，不受影响。

### 8.2 压缩策略

- Starlette gzip：`compresslevel=6`，并跳过 `image/*`、`audio/*`、`video/*`、`application/octet-stream`（`flyai/app.py:613`）；
- nginx（线上已有）：对 JSON 开 gzip/brotli，SSE 路径 `proxy_buffering off; gzip off;`；
- 带 hash 的静态产物：`Cache-Control: public, max-age=31536000, immutable` + `gzip_static`/`brotli_static`；
- 图片目录：`Cache-Control: public, max-age=31536000, immutable`（文件名用内容 hash）。

### 8.3 前端增量落盘

- `db.ts:84 saveSession` 现在整会话 `put`。改为：
  - `messages` 按 `(sessionId, threadId, index)` 或消息 id 单独存储；
  - 会话元数据单独存储；
  - 只写变更的消息与元数据；
- 打开会话：先渲染 IndexedDB，再发条件/增量请求；
- 长会话虚拟列表。

### 8.4 收益

- 消息体不再随 base64 图片膨胀；
- 客户端每次落盘不再结构化克隆整会话（高 CPU / 内存峰值）；
- 首屏更快。

## 9. 与 ST 兼容接口的关系

- ST 的 `/api/chats/get|save` 是全量语义（依据 ST 1.19.1 的 13 条路由，无 append/patch），FlyAI 目前没有实现这些路径；
- 若未来要补适配层：
  - `POST /api/chats/save` 接收完整数组（保持 ST 语义），服务端按消息 id/index **diff 后增量落盘**，避免整文件重写；
  - `POST /api/chats/get` 默认返回全量；FlyAI 前端走扩展参数（`?mode=delta&after=`）拿增量；
  - 请求/响应带 `protocol_version`，便于协商；
- 卡沙箱/作者运行时依赖的 `/api/st/*` 与内存镜像不变，本方案不触碰。

## 10. 迁移与灰度

### 10.1 旧文件

- **读时兼容**：`session_from_dict` 同时支持「两份 override」「仅成员 override」「仅顶层 override」三种形态；
- **写时收敛**：任何一次保存都会按新格式重写，旧文件自然缩容；
- 可选离线工具：`scripts/migrate_session_dedupe.py`（只重写、不删数据，带 `--dry-run`），供线上批量收敛。

### 10.2 客户端灰度

- 用请求头 `X-FlyAI-Client: 2`（或 `?api=2`）标记新客户端；
- 服务端对新客户端：
  - 响应去重（`members[].override = null` + stub）；
  - 提供 `card-bundle` 引用；
  - 支持 `sync` / ETag；
- 旧客户端保持现有响应形状（仍内联 override 与作者脚本），直至 APK 强制更新。

### 10.3 回滚

- 数据格式向前兼容，回滚只需回退代码；读取逻辑同时识别几种形态；
- ETag / sync 是纯新增接口，回滚不影响旧路径；
- 图片外置在灰度期保留 `data` 回退。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 顶层与成员 override 共享引用后被原地修改 | 数据串改 | 现有写路径均为整体赋值；上线前 grep 确认无 `override["x"] = ...` 原地写；必要时读取时 deepcopy |
| `save_merged` 的 `MERGED_FIELDS` 与重建逻辑冲突 | 覆盖丢失 | 重建放在 `get()` 内，`save_merged` 先 `get()` 后合并，天然一致 |
| ETag 未覆盖用户设置/配置变化 | 客户端拿到旧 `st` | ETag 纳入 `settings_mtime_ns` 与 `cfg_rev` |
| 增量同步遇到编辑/删除 | 客户端状态错乱 | 服务端判定前缀不一致即 `reset=true`，客户端回退全量 |
| 世界书按引用后被删除 | 会话丢设定 | 读取时校验 digest，失败回退 override 快照或空并告警 |
| 旧 APK 不认识新响应 | 功能异常 | 按客户端版本双写/回退；灰度期默认旧形状 |
| 导出/压缩依赖完整 override | 导出缺内容 | 导出前从内存对象还原（已有 `effective_character`/`_restore_heavy_extensions` 先例） |
| `regex_scripts` 去重影响 ST 导出 | 卡保真度下降 | 仅在落盘/下发剥离；导出 `to_dict()` 还原 `extensions.regex_scripts` |

## 12. 验收标准

### 12.1 功能

- 旧会话文件（两份 override / 含 `tavern_helper`）可正常打开、聊天、压缩、导出；
- 单 AI 会话保存后磁盘只有一份 override，重新读取后 `effective_character` 结果与改造前一致；
- 群聊多座位不同卡的 override 互不影响；
- `regex_scripts` 在提示词侧、展示侧、导出的行为与改造前一致；
- 编辑/重新生成/撤回/删除/切换分支后，增量同步能正确 reset 或合并；
- 旧 APK 客户端在灰度期功能不变。

### 12.2 性能指标（以本文示例会话为基准）

| 指标 | 现状 | 目标 |
|---|---|---|
| 会话文件 | 11.6MB | ≤4MB |
| 打开会话（未变化） | 传输 10MB+，gzip 1s+ | 304，0 字节 |
| 打开会话（首次，新客户端） | 10MB+ | ≤4MB |
| 新增一条消息后的同步 | 全量 | ≤8KB |
| 首屏消息条数 | 全部 | 最近 50 条 |
| 服务端单轮 CPU（该会话） | 数百 ms~2s | ≤100ms |

## 13. 实施顺序与工作量

| 批次 | 内容 | 预估 | 依赖 |
|---|---|---|---|
| B1 | L1 存储去重（单 AI override、regex_scripts） + 读时重建 | 1–2 天 | 无 |
| B2 | L1 响应去重 + 前端 stub 兼容 | 0.5–1 天 | B1 |
| B3 | L2 卡包接口 + 客户端缓存 | 1–2 天 | B1 |
| B4 | L3 ETag/304（含 `SessionStore.stat`） | 0.5–1 天 | B1 |
| B5 | L3 `sync` / `messages` 分页 + 前端合并 | 2–3 天 | B4 |
| B6 | L4 图片外置 + 懒迁移 | 2–3 天 | B5 |
| B7 | L4 压缩策略 / nginx / IndexedDB 增量 | 1–2 天 | 独立 |
| B8 | 兜底：批量迁移脚本 + 灰度开关 | 1 天 | B1–B6 |

> 预估按熟悉本仓库的开发者计，不含联调与回归时间。

建议里程碑：

- M1（B1+B2+B4）：会话缩容 + 打开会话 304；收益最大、风险最低；
- M2（B3+B5）：卡包缓存 + 增量同步；
- M3（B6+B7）：图片与前端落盘；
- M4（B8）：批量迁移与灰度收尾。
