# 酒馆兼容层差异复核报告

- 复核时间：2026-11-23
- 复核范围：
  - 作者运行时 `webapp/src/services/st/authorRuntime.ts`
  - 卡内运行时 `webapp/src/services/st/cardApp.ts`
  - 两个运行时共享层 `webapp/src/services/st/compat/stCore.js`
  - ST HTTP 兼容 shim（两个运行时里的 `fetch` / `XHR` 本地应答）
  - EJS：`webapp/src/services/st/ejs.ts`、`templateRunner.ts`、`templatePending.ts`、`templatePrompt.ts`、`flyai/template/*.py`
- 对照基准：
  - TavernHelper（`N0VI028/JS-Slash-Runner` 4.12.2）语义，参考本仓库 `docs/酒馆助手全量API语义对照.md` 与 `docs/酒馆助手语义差异清单.md`

  - ST-Prompt-Template（EJS）行为，参考 `docs/酒馆EJS提示词模板兼容方案.md`
- 验证方式：代码逐行静态核对；标注「需核对」的条目依赖上游 `@types/*.d.ts` 的精确签名，本轮未拉取上游源码
- 结论：**阶段 0/1 的修复确实落地了**（事件返回 `{stop}`、世界书数组、`injectPrompts` 返回 `{uninject}`、chatMetadata/IDB/localStorage 桥等），但仍有一批**返回形状、返回类型和作用域语义**与上游不一致；其中 5 项会直接让卡内脚本静默降级或整轮生成失败。

## 1. 作者运行时（authorRuntime.ts）

### 1.1 事件系统

**`eventEmitAndWait` 不等待异步 handler**（`authorRuntime.ts:764-776, 798-799`）

```js
function emit(event){
  ...
  try { results.push(item.fn.apply(null, args)); } catch (e) {}
  return Promise.resolve(results);
}
...
window.eventEmitAndWait = emit;
```

- 上游：`eventEmitAndWait` 等待所有监听器（包括 async handler）完成后再 resolve；
- 本地：只是把返回值收集成数组后立刻 resolve，返回的 Promise 没有被 `await`；
- 影响：`await eventEmitAndWait(...)` 之后读取由 async handler 写出的数据时，数据可能还没到位；
- 说明：`eventEmit` 返回 `Promise<results[]>` 而不是 `Promise<void>` 属于宽松兼容，一般不造成问题。

`eventMakeLast` 与普通 `eventOn` 都是 `push`（`on(...)` 的 `first` 参数只区分 `unshift/push`），若上游 `makeLast` 使用独立的「最后执行」列表，则在注册顺序交错时会不同；需核对上游实现，影响低。

### 1.2 世界书

- `getChatWorldbookName()`（`authorRuntime.ts:1196-1198`）回退链是
  `WORLD.charWorldName || WORLD.name || CHARACTER.name || 'FlyAI'`，**永远非 null**。
  上游未绑定聊天世界书时返回 `null`；卡若用 `if (getChatWorldbookName())` 判断是否存在聊天绑定，会误判。
- `getCharWorldbookNames()`（`:1192-1194`）返回 `{ primary: ..., additional: [] }`，additional 永远为空。
- `getWorldbook(name)`（`:1199`）已改为数组（阶段 0 修复），与上游一致。
- `updateWorldbookWith(name, updater)`（`:1200-1205`）：updater 返回非数组时本地静默返回当前值；上游会以 updater 返回值为准（或报错）。差异小。
- 卡内运行时同名 API 与这里不一致，见第 2 节。

### 1.3 变量

**作用域**（`authorRuntime.ts:1013-1030`）

```js
function currentVariables(option){
  var type = option && option.type ? String(option.type) : 'chat';
  if (type === 'message') { ... }
  return clone(chatStat());          // chat / global / preset / character / script / extension 全部落这里
}
```

- `global/preset/character/script/extension` 全部退化为聊天变量；
- `getGlobalVariables()` 恒 `{}`，`setGlobalVariable()` 恒 `false`（`:1061-1062`）；
- `getContext().variables.global` 用的是另一个 `GLOBAL_VARS`（`:1500-1516`），只在 iframe 内存里，**不持久化**，且与 `getGlobalVariables()` 不是同一份数据；
- 影响：跨聊天设置、全局变量、preset/character 变量全部失效；同一份全局数据两处读写互不可见。

**聊天变量就是 `stat_data`**（`authorRuntime.ts:532-538, 1013-1026`）

- 注入 iframe 的 `CHAT_VARIABLES` 是 `{stat_data: <MVU 变量>}`；
- `chatStat()` 返回 `CHAT_VARIABLES.stat_data`；
- `getVariables({type:'chat'})` 返回 `stat_data` 的内容（扁平）；
- 上游 `getVariables({type:'chat'})` 返回的是 `chat_metadata.variables` 整体（MVU 场景下包含 `stat_data` 键）；
- 影响：
  - 读 `getVariables({type:'chat'}).stat_data` 会得到 `undefined`；
  - 卡往 chat 变量写 `dal_phone` 等键，实际进入 MVU 的 `stat_data` 树，而不是 `chat_metadata.variables` 的兄弟字段；
  - `/api/chats/get` 回读时 `chat_metadata.variables` 被本地拼成扁平 `stat_data`，与 ST 的 `{stat_data:{...}}` 形状不同。

**写接口返回类型 / async updater**（`authorRuntime.ts:1033-1058`）

```js
window.updateVariablesWith = function(updater, option){
  var current = currentVariables(option);
  var next = typeof updater === 'function' ? updater(clone(current)) : current;
  writeVariables(next, option);
  return next;
};
```

- `updateVariablesWith` 不支持 `async` updater：若 updater 返回 `Promise`，`writeVariables` 会把 Promise 当普通对象，经 `clone`（`JSON.stringify`）变成 `{}`；
- 若 updater 只修改传入对象、**没有 return**，`next` 为 `undefined`，`writeVariables` 将其视为 `{}`，**整份变量被清空**。这是最危险的一条；
- `insertOrAssignVariables` / `insertVariables` / `deleteVariable` 都同步返回普通对象，而上游这些写操作通常返回 `Promise`（需核对上游 `@types/function/variables.d.ts`），卡里 `.then()` 会直接报错。

**message 作用域形状**（`authorRuntime.ts:888-893` 与 `compat/stCore.js` `messageData`）

- `getVariables({type:'message', message_id})` 返回 `MESSAGES[index].statData`（扁平）；
- `getChatMessages(...).data` 经 `ST.messageData` 返回 `{stat_data: raw.statData}`；
- 上游两者是同一份消息变量对象。本地同一份数据有这两种形状，卡的两种写法只有一种能工作。

### 1.4 消息

- **删除/轮转不落库**（`authorRuntime.ts:1783-1805`）：`deleteChatMessages` / `rotateChatMessages` 只 `splice`/重排本地数组，未调用任何宿主消息接口；刷新后恢复。
- **窗口与楼层号**（`authorRuntime.ts:74,146`）：`authorRuntimeMessages` 只保留最近 200 条（`slice(-MAX_MESSAGES)`），`message_id` 是窗口内下标，不是真实楼层号。超过 200 条的会话，`getChatMessages(0)`、区间读取、持久化的楼层锚点都会偏移。
- **隐藏楼层**：前端 `mapMessage`（`webapp/src/services/chat/store.ts:479`）直接丢弃 `hidden` 消息，因此运行时镜像里没有隐藏楼层；`hide_state` 过滤没有意义，楼层号也与后端真实下标不一致。
- **`setChatMessages` 只落库部分字段**（`authorRuntime.ts:1750-1781` + `flyai/api/routes_session.py:684-751`）：
  - 会落库：`message`、`is_hidden`、`data.stat_data`、`extra`；
  - 不落库：`name`、`role`（本地镜像改了，宿主不变）；
  - `options.refresh` 被忽略。
- **`getChatHistoryDetail`**（`authorRuntime.ts:1670-1690`）：返回 `{ [file_name]: ChatMessage[] }`。上游返回值疑似为每个文件的 JSONL 文本（`Record<string, string>`），需核对；若确实为字符串，这里是形状不一致。
- **`retrieveDisplayedMessage`**（`:1493-1496`）：返回镜像原文，不经过展示侧正则/宏，也不是 DOM 实际渲染结果。

### 1.5 注入与生成

- **`injectPrompts` 丢参数**（`authorRuntime.ts:1807-1822`；宿主 `AuthorPanelFrame.tsx:474-484`；服务端 `routes_session.py:824-845`、`routes_chat.py:928-940`）：
  - iframe 侧 `clone(prompts)` 会把 `filter` 函数丢掉；
  - 服务端只保留 `id/content/position/depth/scan/role`，但注入时 `_author_prompt_extra` **只拼 content**，`position/depth/role/scan` 全部忽略，统一追加到 system prompt 末尾；
  - 上游 `position:'in_chat'`、`depth:0` 的注入会落在历史末尾，这里是 system 前缀，位置语义完全不同。
- **`context.generate('normal')`**（`authorRuntime.ts:2165-2171`）：
  - 带 `quiet_prompt` 时走 `MSG_GENERATE_MAIN` → 宿主 `generateCardReply`，会追加 AI 楼层（阶段 1 修复）；
  - 不带 `quiet_prompt` 时退回 `__flyaiGenerate` 独立文本生成，不产生楼层、不派发 `MESSAGE_RECEIVED`；
  - 上游 `context.generate('normal')` 始终是主聊天生成。
- **`context.generate` 返回 `true`**（`requestGenerateMain` → `settleMainGenerate`）而不是上游的生成结果/消息；通常卡只 `await`，影响低。

### 1.6 角色 / 宏 / Slash

- `getCharacter()`（`:1866`）返回 `{name, description, avatar}` 的克隆；缺 `first_messages`、`extensions`、`worldbook`、`creator_notes` 等。
- `getCurrentCharacterId()` 返回 `avatar || name`；`getCharacterNames/Ids` 只返回当前角色。
- `substitudeMacros`（`:2000-2010`）只展开 `{{char}}`、`{{lastMessage}}`；卡内版多了 `{{user}}`、`{{charAvatar}}`、`{{getvar::}}`。
- `triggerSlash`（`:1970`）执行少量命令后固定返回 `''`；上游返回管道结果（`/getvar::x` 取变量等）。
- `SillyTavern.getContext()`（`:1617-1668`）只有约 29 个字段（上游 114）；`extensionPrompts` 恒 `{}`；`getPresetManager()` 恒 `null`；`saveSettingsDebounced()` 空实现。

## 2. 卡内运行时（cardApp.ts）

### 2.1 世界书读权限被写权限门控（影响最大）

```js
// cardApp.ts:1373-1386
window.getCharWorldbookNames = function(){
  if (!CAP_WRITE) return { primary: null, additional: [] };
  ...
};
window.getWorldbookNames = function(){ return CAP_WRITE ? worldbookNames() : []; };
window.getWorldbook = function(name){
  if (!CAP_WRITE) return [];
  return worldEntriesArray();
};
```

`CAP_WRITE` 来自 `capabilities.write`（`:570`），默认对应用户设置 `st_card_write_enabled=false`。因此**默认配置下卡应用读不到任何世界书**。上游读接口不受写权限影响。这会让《约会大作战》这类用 `Array.isArray(getWorldbook(...))` 判断能力的卡直接降级。

### 2.2 `getWorldbook(name)` 忽略书名

`:1382-1386` 与 `:1353-1357`：无论传什么名字，都返回「角色卡世界书 + 会话挂载世界书」的合并数组；`updateWorldbookWith`/`replaceWorldbook` 写回也写到同一份（挂载书或角色副本 table）。多世界书卡会串书。

作者运行时按 `worldbookOf(name)` 解析，行为更接近上游 —— 两个运行时因此不一致。

### 2.3 消息变量

```js
// cardApp.ts:538-558（宿主注入的 chat seed）
variables: item.statData && typeof item.statData === 'object'
  ? { stat_data: item.statData } : undefined
```

但共享层 `ST.messageData`（`compat/stCore.js`）只认 `raw.data` / `raw.statData`：

```js
ST.messageData = function (raw) {
  if (raw.data && typeof raw.data === 'object' && !Array.isArray(raw.data)) return raw.data;
  if (raw.statData && typeof raw.statData === 'object') return { stat_data: raw.statData };
  return {};
};
```

卡内镜像的字段名是 `variables`，所以：

- `getChatMessages(...)` 返回的 `data` 恒为 `{}`；
- `swipes_data` 也全部是 `{}`；
- 只有 `getChatMessages` 的 synthetic 兜底分支（单条、无镜像时）才手动填了 `data: {stat_data: VARIABLES}`（`:1163-1176`）。

作者运行时传入的是带 `statData` 的 `MESSAGES`，所以没有这个问题 —— 两个运行时不一致。

### 2.4 消息窗口：取最旧 200 条

```js
// cardApp.ts:538-539
.slice(0, MAX_CARD_CHAT_MESSAGES)   // 200
```

作者运行时是 `slice(-200)`（取最新）。卡内取最旧 200 条意味着**超过 200 条的会话里，卡应用看不到最近的消息**，且 `getChatMessages('latest')` 返回的是第 199 条。这比「楼层号偏移」更严重。

### 2.5 其他

- `getVariables(options)`（`:1275-1279`）：`chat` 与 `message` 都返回 `VARIABLES`，`global` 返回 `{}`；不区分 message_id。
- `getGlobalVariables()` 恒 `{}`（`:1296`）。
- 事件、`injectPrompts`、`delete/rotate`、`getChatHistoryDetail`、`retrieveDisplayedMessage`、`triggerSlash`、宏替换与作者运行时同源问题。

- `getChatWorldbookName()`（`:1379-1381`）返回 `WORLD_NAME || CHAR_WORLD_NAME || null`，是正确语义；作者运行时却永远非 null（见 1.2）。

## 3. ST HTTP 兼容 shim（两个运行时）

## 4. EJS（ST-Prompt-Template）

### 4.1 编译器本身

`ejs.ts` 支持 `<% %>`、`<%= %>`、`<%- %>`、`<%# %>`、`<%_ _%>`、`-%>`、`<#escape-ejs>`，并在 `%>` 查找时正确处理字符串/注释；提示词侧通过 `escapeOutput:false` 让 `=` 与 `-` 等价（`templatePrompt.ts:37`），输出侧默认 HTML 转义（`templatePending.ts:83`）。这部分与设计一致。

未实现的 EJS 语法：
- `<%%` / `%%>`（字面量 `<%` / `%>`）不支持；
- `include` / 自定义 `delimiter` 不执行（文档已声明）。

### 4.2 宿主 API：桩实现 / 直接抛错

`templateRunner.ts:227-275` 的 `api` 对象：

```js
getwi: () => null,
getpreset: () => null,
injectPrompt: readOnly,
activewi: readOnly,
activateRegex: readOnly,
evalTemplate: readOnly,
```

而 `readOnly()` 是 `throw new Error('输出侧模板不允许调用注入/激活类 API')`。问题在于**提示词侧和输出侧共用同一个 `api`**：提示词侧 `escapeOutput:false` 只影响转义，不会放开这些函数。因此任何在提示词模板里调用 `injectPrompt`/`activewi`/`evalTemplate` 的卡都会抛错。

服务端 `flyai/template/prompt.py:252-256` 对 `errors` 非空直接抛 `TemplatePromptError` → **整轮生成中止**，不是降级。

同类后果：
- `getwi('xxx')` 返回 `null`，`getwi(...).content` 抛 TypeError；
- 未提供 `_`（lodash）/`faker`，模板里 `_.get(...)` 抛 ReferenceError；
- `variables` 只有合并视图，没有 `cache`/`initial` 作用域，也没有 `variables.local/global/message` 子对象；
- `getChatMessage/getChatMessages` 返回 `{index, role, name, content}`，不是 ST 消息形状（`.mes`、`.is_user`、`.extra` 为 `undefined`）；
- `getMessageVar/setMessageVar`：提示词侧上下文没有 `messageId`（`prompt.py:_context`），`String(id) !== messageId` 恒成立 → 永远返回 `undefined` / 不写入；
- `substituteParams` 只展开 `{{char}}/{{user}}/{{group}}`。

设计文档里这些 API 标记为 ✅（`docs/酒馆EJS提示词模板兼容方案.md` 第 869-880 行），代码实际是 ❌/桩 —— 文档与实现不一致，需要对齐。

### 4.3 作用域与标记

- 服务端 `vars.py:SCOPES = ("message","local","global")`，没有 `cache` / `initial`；
- 全仓库没有任何 `[GENERATE:*]`、`[RENDER:*]`、`[InitialVariables]`、`@@` 装饰器、`@INJECT` 的处理代码（grep 无命中）；
- 使用这些写法的卡，模板不会被注入/装饰器不会生效，通常表现为「变量不更新」「状态栏不显示」，不会报错（除模板本身报错外）。

### 4.4 输出侧

- **不跳过代码围栏**：`templatePending.ts:76-88` 把整条 `rawContent` 交给 EJS；ST-Prompt-Template 明确不执行代码块里的 `<% %>`（见 `docs/酒馆EJS提示词模板兼容方案.md` §1.1 第 4 条）。模型如果回复里给出模板示例，会被实际执行。
- **提示词侧历史不执行模板**：`prompt.py:_collect` 只收 `template_source=True` 的消息；聊天历史、用户消息只剥离标记。ST-Prompt-Template 在每次组装提示词时会重算消息里的模板。历史状态栏不会随当前变量刷新。
- 单元格输出 >64KB、总输出 >512KB、任一单元格报错 → 整轮中止（安全取舍，但比上游严格）。

### 4.5 与 EJS 上游一致的部分

- `<%=` 转义、`<%-` 原样、`<%#` 注释、空白裁剪、`<#escape-ejs>`；
- 提示词侧 `=`/`-` 等价；
- `getvar/setvar/incvar/decvar/unsetvar/hasvar` 与 `global/local/message` 三种作用域的基础读写；
- `setvar` 写入以 ops 回传、服务端校验后生效；
- `getchar/getuser/getgroup/getContext` 的简化视图。
