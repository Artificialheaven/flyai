# 酒馆插件加载可行性评估报告

- 评估时间：2026-11-24
- 评估对象：FlyAI 现有酒馆兼容层
  - `webapp/src/services/st/cardApp.ts`
  - `webapp/src/services/st/authorRuntime.ts`
  - `webapp/src/services/st/compat/stCore.js`
  - `webapp/src/services/st/native/stNative.ts`、`native/ejsRuntime.ts`
  - `flyai/api/routes_session.py` 中的 `/st/*` 路由
- 对照基准：SillyTavern 1.19.1、JS-Slash-Runner（酒馆助手）4.12.2
- 方式：只读静态核对（代码、docs、本地 ST 上游仓库），未修改任何代码

**配套文档**

- `docs/酒馆插件模块与符号覆盖矩阵.md`：38 个宿主模块、184 个符号的逐项覆盖与定义
- `docs/酒馆插件兼容施工方案.md`：分级兼容、扩展宿主、API、里程碑、测试与文件清单

---

## 0. 结论

**现有兼容层是“酒馆卡内脚本的宿主仿真”，不是“酒馆扩展加载器”。**

它已经能把角色卡里 `extensions.tavern_helper.scripts` 这一层脚本跑起来（红楼、约会大作战已实测），也能让卡内代码 `import('/script.js')` 这类路径命中 ST 形状的模块。但它**不具备直接加载现成 SillyTavern 第三方扩展的能力**：

- 没有扩展包格式、安装/更新/启停、manifest、加载顺序、hooks、扩展设置持久化；
- 没有 ST 主页面 DOM 和扩展 UI 挂载点；
- 只仿真了 20 个 ST 前端模块，且是有选择的只读子集；
- 扩展大量依赖的 `popup.js`、`slash-commands/*`、`secrets.js`、`constants.js`、`i18n.js` 等模块不存在；
- 沙箱是 null-origin + `connect-src 'none'`，扩展的联网、密钥、文件能力都没有宿主通道。

一句话概括潜力：**骨架可复用，逻辑型扩展是可行的中期目标，UI 型扩展不建议直接兼容，现成扩展“装上就能跑”不现实。**

| 目标 | 当前状态 | 判断 |
|---|---|---|
| 卡内 tavern_helper 脚本 | 两张卡实测可跑，通用卡仍有缺口 | ✅ 已具备（部分） |
| 第三方“逻辑型”扩展（只跑事件/变量/生成/世界书/slash） | API 与模块面缺口大 | 🟡 有潜力，需要新建扩展宿主，约 4–8 周 |
| 第三方“UI 型”扩展（设置面板、聊天区注入、弹窗） | 无 ST DOM/UI 体系 | 🔴 低可行性，月级投入且脆弱 |
| 依赖外部 API、密钥、文件的扩展 | 无 secrets、无通用网络通道 | 🔴 不建议 |
| ST 服务端插件（`/plugins`、Express 路由） | 机制完全不同 | ⛔ 不适用 |

> 注意：FlyAI 自身已有一套 Python 工具插件体系（`plugins/` + `manifest.json` + `setup(registry)`），和 SillyTavern 前端扩展不是同一概念，本报告不涉及。

## 1. 现有兼容层到底是什么

### 1.1 两个运行时

| 运行时 | 入口 | 运行的代码 |
|---|---|---|
| 消息卡内应用 | `cardApp.ts` | 消息正文里的整页 HTML/JS（开场页、手机、终端等） |
| 作者运行时 | `authorRuntime.ts` | 角色卡 `extensions.tavern_helper.scripts` 里的 JS-Slash-Runner 脚本 |

`authorRuntime.ts:1-13` 的注释已经明确：它把“卡内 tavern_helper 脚本原本运行在酒馆助手 `about:srcdoc` iframe”这件事，改成了在 FlyAI 自己的沙箱 iframe 里重放。服务端只下发卡里的脚本正文，不加载酒馆助手扩展本体。

### 1.2 共享的宿主仿真层

- `compat/stCore.js`：ST 消息形状、消息范围、变量深合并、世界书数组语义、82 个 `tavern_events` + 7 个 `iframe_events` 常量。
- `native/stNative.ts`：把会话整理成 ST 形状的快照 `__FLYAI_ST_NATIVE__`，并用 `import map` + `data:` 模块仿真 20 个 ST 前端模块（`NATIVE_MODULES`，`stNative.ts:1052`）。
- 两个运行时各自注入：
  - `window.SillyTavern.getContext()`（约 29/114 字段）；
  - `window.TavernHelper`（约 27/137 个同名函数）；
  - `eventSource` / `eventOn` / `triggerSlash` / 变量 / 世界书 / 消息 / 生成桥；
  - jQuery、lodash、Zod、`EjsTemplate`、`toastr`、部分 `Popup`。

### 1.3 HTTP 桥

`cardApp.ts:2922`、`authorRuntime.ts:1590` 的 `chatApiFetch` 在 iframe 内本地应答：

- `/api/backends/chat-completions/generate|status`
- `/api/settings/get|save`
- `/api/extensions/discover|version|*`
- `/api/presets/*`、`/api/tokenizers/*`
- `/api/chats/get|save|rename|delete`
- `/api/users/me`、`/api/files/sanitize-filename`
- `/api/worldinfo/*`

其中 `/api/extensions/*` 是**固定合成值**，不是真实扩展管理：

```js
// authorRuntime.ts:1636
return Promise.resolve(jsonResponse([
  { name: 'JS-Slash-Runner', type: 'local', enabled: true, version: '1.12.6' },
  { name: 'ST-Prompt-Template', type: 'local', enabled: true, version: '1.0.0' }
]));
```

### 1.4 安全边界

两个 iframe 都是 `sandbox="allow-scripts"` 的 null-origin 沙箱，CSP 里 `connect-src 'none'`：

- `cardApp.ts:439` `contentSecurityPolicy()`
- `authorRuntime.ts:573` 同款策略

模型调用统一走宿主桥，不把登录态/Bearer 放进 iframe。这是很好的安全底座，但也意味着**任何需要真实网络、密钥、本地文件的扩展都必须新增宿主通道**。

## 2. “酒馆插件”的三种含义与现状

| 类型 | 典型形态 | 现有支持 | 说明 |
|---|---|---|---|
| 卡内 TavernHelper 脚本 | 角色卡 `extensions.tavern_helper.scripts` | 🟡 部分 | 已能跑两张重点卡；API 面 27/137 |
| 第三方前端扩展 | `public/scripts/extensions/third-party/<name>/manifest.json + index.js + css` | 🔴 无 | 没有扩展宿主、没有 loader、没有 UI |
| ST 服务端插件 | 服务端 `plugins/`、Express 路由、secrets | ⛔ 无 | 与前端兼容层不在一个层面 |

如果需求只是“让卡自带的脚本跑起来”，现有层已经走在这条路上；如果需求是“像酒馆一样安装 `.zip` / Git 扩展并生效”，那是另一套产品能力。

## 3. 量化证据：离“直接加载”还差什么

### 3.1 TavernHelper / context API 面

按仓库已有对照文档：

| 面 | 上游 | 本地同名 | 覆盖率 |
|---|---:|---:|---:|
| `TavernHelper.*` 函数 | 137 | 27 | 19.7% |
| `tavern_events` 常量 | 82 | 82 个常量已补 | 常量齐，语义/派发未全对齐 |
| `SillyTavern.getContext()` 字段 | 114 | 29 | 25.4% |

来源：`docs/酒馆助手API覆盖对比.md:12-16`、`docs/酒馆助手兼容检查进度.md:10-14`。

已确认的语义缺口（`docs/酒馆兼容层差异复核报告.md`）包括：

- `setChatMessages` / `deleteChatMessages` / `rotateChatMessages` 落库不完整；
- `context.generate('normal')` 不产生主聊天楼层；
- `injectPrompts` 的 position/depth/role/filter 语义不完整；
- 全局变量不持久化；
- 宏覆盖极少；
- `triggerSlash` 只识别少量命令且返回值恒为空；
- `eventMakeFirst/Last` 没有真正的插队语义；
- 隐藏楼层、绝对楼层号、展示消息等仍有偏移。

这些不是“扩展加载”的独有问题，但会同时限制扩展的可用性。

### 3.2 ST 前端模块面（关键差距）

我用本地 ST 1.19.1 仓库统计了**内置扩展**实际 import 的核心模块和符号，再与本地 `stNative.ts` 的仿真面比对：

- 内置扩展共 import **41 个模块路径**，其中 **38 个是宿主相关模块**（另 3 个是 quick-reply 自己的内部模块）；
- 本地 `NATIVE_MODULES` 只有 **20 个路径**，其中与这 38 个重合的约 **11 个**；
- 对重合模块，符号覆盖率也很低：

| 模块 | 扩展 import 的符号数 | 本地导出命中 | 覆盖率 |
|---|---:|---:|---:|
| `script.js` | 42 | 10 | 24% |
| `utils.js` | 41 | 11 | 27% |
| `extensions.js` | 16 | 3 | 19% |
| `popup.js` | 4 | 0 | 0% |

缺失的高频模块（均有多个内置扩展依赖）：

- `slash-commands/SlashCommandParser.js`、`SlashCommand.js`、`SlashCommandArgument.js` 等整套 slash 框架
- `popup.js`（`Popup`、`callGenericPopup`、`POPUP_TYPE`、`POPUP_RESULT`）
- `secrets.js`（11 处 import）
- `constants.js`、`i18n.js`
- `RossAscends-mods.js`、`reasoning.js`、`textgen-settings.js`
- `util/AccountStorage.js`、`macros/macro-system.js`
- `dragdrop.js`、`tool-calling.js`、`nai-settings.js`

一个具体且致命的例子：内置扩展会写

```js
import { eventSource, event_types } from '../../../script.js';
```

但本地 `SCRIPT_JS_SOURCE` 没有导出 `eventSource` / `event_types`（它们只出现在 `scripts/events.js` 的仿真里）。

**ES module 的命名导入是链接期解析的**：只要目标模块少一个被导入的具名导出，整个模块图加载失败，扩展完全不会执行。现有文档里设想的“未实现导出给诊断桩、访问时再抛错”对 `import { x }` 无效，必须为每个可能被导入的名字真实生成一个导出（或按需实现）。这是扩展兼容工作量的主要来源之一。

### 3.3 扩展生命周期（完全没有）

ST 的扩展加载流程（`public/scripts/extensions.js`）：

1. `discoverExtensions()` 发现扩展目录；
2. `getManifests()` 读取每个 `manifest.json`；
3. 按 `loading_order` 排序，检查 `requires`、`dependencies`、`minimum_client_version`、`disabledExtensions`；
4. `import('/scripts/extensions/<name>/<js>')` 加载 ES module；
5. 注入 CSS、i18n；
6. 调用 manifest `hooks.activate`（以及 install/update/delete/enable/disable/clean）；
7. `extension_settings` 与 `saveSettingsDebounced()` 做设置持久化。

FlyAI 当前**一项都没有**：

- 没有扩展目录/包格式/安装位置；
- 没有 manifest 解析；
- 没有启停、顺序、依赖；
- 没有 hooks；
- `extension_settings` 只来自快照，`saveSettingsDebounced()` 是空函数（`stNative.ts` 的 `SCRIPT_JS_SOURCE`）；
- 后端 `/api/extensions/install|update|delete|version` 全部没有；
- 市场 `KINDS = ("character", "world", "preset", "session")`，没有扩展类型（`flyai/market/models.py:14`）。

### 3.4 UI / DOM（UI 型扩展的硬阻塞）

ST 的扩展 UI 主要挂在主页面的这些节点上：

- `index.html:5773` `#extensions_settings`
- `index.html:5791` `#extensions_settings2`
- `#extensionsMenu`、`#leftSendForm`、`#extensions_details`
- 以及大量 jQuery、Popper、`Popup`、`toastr`、拖拽、抽屉、富文本/图片控件。

FlyAI 作者运行时只造了一个很小的假 DOM：

- `#chat`、`.mes[mesid]`、`.mes_text`
- 隐藏的 `#send_textarea`、`#send_form`、`#extensionsMenu`、`#top-settings-holder`

没有 `#extensions_settings` / `#extensions_settings2`，没有设置面板、抽屉、弹窗体系，也没有 ST 的完整 CSS。UI 型扩展即使模块都能 import，拿到 `null` 的挂载点后也会大面积失败。

### 3.5 网络与密钥

- 扩展经常直连外部服务（TTS、翻译、向量、图片、搜索、WebLLM 等），或通过 Extras/自定义 API；
- 当前 CSP `connect-src 'none'`，未登记的请求一律拒绝；
- 没有 `secrets.js`、没有 `/api/secrets/*`、没有通用文件上传/下载；
- 如果要放开，必须设计宿主代理 + 每扩展权限（类似现有卡沙箱的 `st_net` 策略），否则等于把任意远程代码和密钥接进用户会话。

### 3.6 扩展包本身

ST 扩展不是“一段脚本”，而是：

```text
third-party/<name>/
  manifest.json   # display_name / loading_order / js / css / hooks / requires / dependencies
  index.js        # ES module，import 大量 ST 内部模块
  style.css
  locales/、templates/、assets/、子模块…
```

它还允许 `import()`、`import.meta.url`、`fetch('/scripts/extensions/...')` 取自己的模板/资源。当前沙箱是 null-origin + `data:` 模块，既没有扩展的 URL 空间，也没有静态资源路由；直接搬过来会遇到模块解析、资源路径、CSP 三重问题。

## 4. 潜力评估

### 4.1 可复用的骨架（这是“有潜力”的部分）

现有实现里有几块做对了，值得保留：

1. **快照 + 模块仿真**：`__FLYAI_ST_NATIVE__` + `data:` 模块 + import map，证明可以在隔离环境里伪造 ST 模块路径；
2. **统一宿主桥**：生成、消息、世界书、变量、元数据都有落库协议，扩展需要的核心数据通道已有雏形；
3. **事件总线与兼容核心**：`stCore.js` 已经把 ST 消息/变量/世界书/事件形状收敛到一处；
4. **能力门控**：`CAP_WRITE`、`CAP_ACTIONS`、`st_image/st_net` 这类策略，为“扩展权限”提供了现成范式；
5. **测试底座**：ST 相关前端测试 13 个文件、整套后端测试，适合做逐扩展冒烟。

### 4.2 分级可行性

| 层级 | 内容 | 可行性 | 大致工作量 |
|---|---|---|---|
| T0 | 继续完善卡内 tavern_helper 脚本 | 高 | 按缺口逐项，周级 |
| T1 | 无 UI 的“逻辑型”扩展：只监听事件、读写变量/世界书、调生成、注册 slash | 中 | 4–8 周（扩展宿主 + 生命周期 + slash + 模块面） |
| T2 | 带设置面板/聊天区注入的 UI 扩展 | 低 | 2–3 个月起，且只能覆盖少量扩展 |
| T3 | 依赖外部 API/密钥/本地文件/服务端路由的扩展 | 很低 | 不建议 |

### 4.3 为什么 T2 不推荐

UI 扩展的兼容面是**没有边界的**：它们可以查询任意 ST DOM、改任意全局、依赖 ST 的 CSS 类名和布局、用 jQuery 插件、监听 ST 内部事件顺序。要做到“装上就能跑”，等价于在 FlyAI 里重建一遍 ST 主界面。投入产出比远低于把这部分能力做成 FlyAI 原生面板/扩展 API。

## 5. 如果确实要做，推荐路线

### 5.1 先定义契约，不要承诺“直接兼容”

给扩展 manifest 增加 FlyAI 侧声明，例如：

```json
{
  "flyai": {
    "compat": "logic",
    "capabilities": ["chat.read", "chat.write", "generate", "worldbook.read"],
    "host_api": 1
  }
}
```

没有声明的扩展默认不加载，避免“装了但半死不活”。

### 5.2 新建“扩展宿主”，不要继续往卡运行时里塞

- 独立的 extension host iframe（逻辑型可隐藏，UI 型可选可见）；
- 与 cardApp/authorRuntime 共用 `stCore`、快照、fetch 桥，但不共用“卡脚本”语义；
- 宿主侧新增 extension manager：
  - 安装（zip / Git URL）、更新、删除、启停、排序；
  - 存储到 `data/extensions/<name>/`；
  - manifest 校验、版本/依赖检查、hooks；
  - 扩展设置持久化到用户设置或会话设置。

### 5.3 按依赖频率补模块与符号

优先级建议：

1. `script.js` 补 `eventSource`、`event_types`、`getRequestHeaders`、`generateQuietPrompt`、`generateRaw`、`messageFormatting`、`substituteParamsExtended`、`extension_prompt_*` 等；
2. `utils.js` 补 `getStringHash`、`getBase64Async`、`download`、`saveBase64AsFile`、`getSanitizedFilename`、`regexFromString`、`clamp` 等；
3. `extensions.js` 补 `renderExtensionTemplateAsync`、`writeExtensionField`、`saveMetadataDebounced`、`getApiUrl`、`doExtrasFetch`；
4. 新增 `popup.js`（至少 `Popup`/`callGenericPopup`/`POPUP_TYPE`/`POPUP_RESULT`）；
5. 新增 `slash-commands.js` 与 `slash-commands/*`；
6. 再按实际扩展补 `secrets.js`、`constants.js`、`i18n.js`、`RossAscends-mods.js`、`reasoning.js`、`textgen-settings.js`、`AccountStorage.js`、`macro-system.js`。

实现方式建议：**从 ST 源码/类型定义自动生成导出清单**，为未实现的名字生成显式抛错桩。ES module 不能靠 Proxy 兜住未知命名导入，必须“名字先存在”。

### 5.4 补 slash 与事件

- `SlashCommandParser.addCommandObject`、`SlashCommand.fromProps`、`SlashCommandArgument`、`SlashCommandEnumValue`；
- 解析器至少支持现有卡的 `/send`、`/trigger`、变量命令，并返回管道结果；
- `eventSource.on/off/emit/emitAndWait/removeListener` 与 `event_types` 对齐；
- 修正 `eventMakeFirst/Last` 的真实顺序语义。

### 5.5 网络与权限

- 不放开 iframe 的 `connect-src`；
- 所有外部请求走宿主代理，按 manifest 声明的域名白名单；
- 密钥只存在宿主，扩展拿不到明文；
- 安装远程扩展要有审核/签名/来源提示，扩展代码属于可执行供应链。

### 5.6 UI 策略

不建议做“ST DOM 全仿真”。更现实的做法：

- 给扩展提供 FlyAI 原生面板 API（React 侧渲染设置项）；
- 或提供“扩展面板 iframe”契约，扩展按 FlyAI 的少量约定渲染，而不是按 ST 的 DOM 约定；
- 只对少数高价值扩展做定点适配（类似现在对红楼/约会大作战做的卡特定补丁）。

### 5.7 验收方式

- 兼容矩阵：扩展名 / 所需模块 / 所需 API / 结果；
- 每个支持扩展一个冒烟用例；
- 明确“支持 / 降级 / 不支持”，不要静默失败。

---

## 6. 不建议的做法

1. **宣传“直接加载酒馆插件”**：现成扩展的模块面、DOM、网络、生命周期都不满足，用户预期会落空。
2. **尝试加载 JS-Slash-Runner 扩展本体**：项目已经选择重写它的 API（27/137），再用完整扩展反而会引入整套 ST 主界面依赖。
3. **在 `stNative.ts` 里逐个手工补导出**：扩展生态变化快，必须自动生成导出清单 + 诊断桩。
4. **为了 UI 扩展重建 ST 主页面**：成本高、维护重、兼容永远追不上。
5. **无条件放开网络和 secrets**：扩展是远程可执行代码，必须按能力授权。

## 8. 最终判断

- **作为“酒馆卡脚本兼容层”**：方向正确，已具备继续补齐的基础；短期应优先补 T0 的语义缺口（消息落库、生成楼层、slash、宏、全局变量、隐藏楼层）。
- **作为“酒馆扩展加载器”**：当前不具备直接加载能力；架构有约三成可复用的骨架，适合先做“逻辑型扩展宿主”这一中间形态。
- **直接加载现成酒馆插件（尤其 UI 型）**：不建议作为产品目标；如果必须做，应按“扩展兼容等级 + 能力声明 + 白名单适配”的方式交付，而不是宣称通用兼容。
