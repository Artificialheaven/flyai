# 酒馆插件 L3 可行性评估与实施方案

- 日期：2026-11-25
- 前置：L1（逻辑型宿主）与 L2（schema / panel.html / 消息挂件）已落地
- 目标：**在不重写 FlyAI 主界面的前提下，尽可能让依赖 ST DOM/UI 的插件可用**
- 结论：可行，但要按“兼容壳（ST-like shell）+ 分级开放”的方式做，不能承诺“任意 UI 插件装上就能跑”

## 0. TL;DR

| 方案 | 判断 |
|---|---|
| A. 独立“ST 兼容壳”iframe（自建 ST 形状 DOM/CSS，扩展在其中运行） | ✅ **推荐**，兼容设置面板/菜单/消息区挂件/部分聊天区渲染 |
| B. 直接内嵌整套 SillyTavern 前端 | ⛔ 不推荐：AGPL 传染、后端接口/路由全量适配、维护双份 UI |
| C. DOM 代理/翻译层（把 jQuery 选择器映射到 React） | ⛔ 不可维护：选择器/布局/事件顺序无边界 |

建议：**A + 分级开放**。默认仍只跑 L1/L2；L3 需要管理员开启 + 单扩展显式启用，
并展示“兼容模式”警告。先做面板/菜单/消息挂件（覆盖大部分 UI 扩展），
再评估是否做“兼容视图”接管聊天区渲染。

## 1. 目标与边界

### 1.1 要做到

- 现有 ST 扩展不改代码即可加载；
- 能挂载到 `#extensions_settings` / `#extensions_settings2` / `#extensionsMenu`；
- 能查询/读改 ST 形状的消息 DOM（`.mes[mesid]`、`.mes_text`、`.mes_block`）；
- 能在消息上注入按钮/徽标/图片，并响应点击；
- 能用 jQuery、Popper、DOMPurify、morphdom、Fuse、hljs；
- 设置、事件、slash、生成、世界书、网络仍走 FlyAI 宿主能力；
- 出错只影响该扩展/该壳，不影响聊天主界面。

### 1.2 不做

- ST 服务端插件、Express 路由、Extras；
- 任意远程脚本；
- 让扩展拿到 Bearer/Cookie/密钥；
- 逐像素复刻 ST 皮肤/主题（只保证结构+基本样式兼容）。

## 2. L3 插件到底用哪些 UI 面

对 ST 1.19.1 内置扩展与常见第三方的静态归纳：

| UI 面 | 典型用途 | 兼容难度 |
|---|---|---|
| `#extensions_settings` / `#extensions_settings2` | 设置面板、抽屉、折叠块 | 中：需要容器 + 抽屉 + 表单控件 |
| `#extensionsMenu` | 扩展菜单按钮（弹出小面板） | 中：菜单容器 + 定位 |
| `.mes` / `.mes_text` / `.mes_block` | 消息渲染、注入按钮/徽标/图片 | 高：消息镜像与写回 |
| `#send_textarea` / `#send_form` / `#leftSendForm` | 输入框、发送按钮旁挂件 | 中：双向同步 |
| `#chat` 滚动容器 | 滚动、定位、虚拟化假设 | 高 |
| `#top-settings-holder`、`#rightNavHolder` | 顶栏/侧栏按钮 | 高（FlyAI 布局不同） |
| `#movingDivs` / jQuery UI | 可拖拽浮动面板 | 很高 |
| ST CSS 类名/主题变量 | 视觉一致 | 高：只做基础变量 |

结论：**设置/菜单/消息挂件覆盖大多数“功能型 UI 插件”；聊天区渲染改写和拖拽面板是长尾。**

## 3. 方案对比

### A. ST 兼容壳 iframe（推荐）

在 FlyAI 页面里放一个隐藏/可展开的 iframe，内部自建 ST 形状的 DOM 骨架：

```
#flyai-st-shell
  #chat (镜像消息列表)
    .mes[mesid] > .mes_block > .mes_text / .mes_buttons
  #extensions_settings
  #extensions_settings2
  #extensionsMenu
  #leftSendForm / #send_form / #send_textarea
  #movingDivs
  #popup_container
```

- 扩展入口、import map、全局 shim 复用 L1 宿主；
- 壳里额外提供 jQuery/Popper/DOMPurify/morphdom 等真实库；
- 消息列表由宿主快照渲染，事件更新；
- 扩展对 DOM 的修改留在壳内，可选“写回消息文本”（默认关）；
- 设置类 UI 在抽屉里展示给用户；消息挂件通过壳内 DOM 注入，渲染在壳的消息镜像上。

优点：隔离、可逐步扩展、失败不影响主界面；
缺点：壳与 FlyAI 主消息列表是两份渲染，需要同步；聊天区滚动/布局不完全一致。

### B. 内嵌整套 ST 前端

- 直接把 ST `public/` 作为第二前端，替换 API 层；
- 兼容性最高，但：
  - ST 是 **AGPL-3.0**，分发会带来许可证义务；
  - 需要适配所有 `/api/*`、用户体系、主题、移动端；
  - 两套 UI 维护成本极高，FlyAI 自身功能（会话/内容库/模型）要二次实现。
- 不建议作为产品路线，除非目标是“ST 套壳”。

### C. DOM 代理层

- 在 FlyAI React 页面上伪造 ST DOM，让扩展直接操作；
- jQuery 选择器、CSS、布局、事件顺序无边界，任何组件重渲染都会破坏；
- 维护成本高于 A，且无法隔离。

## 4. 推荐架构（A）

```
FlyAI 页面
├─ 聊天主界面（React，不变）
├─ 扩展抽屉（React）
│   └─ <iframe sandbox=allow-scripts>  ← ST 兼容壳
│        ├─ ST-like DOM 骨架 + 基础 CSS
│        ├─ jQuery / Popper / DOMPurify / morphdom / Fuse / hljs
│        ├─ L1 host shims（事件/设置/生成/slash/fetch）
│        ├─ import map（38+ 模块）
│        └─ 扩展入口模块（按 loading_order）
└─ ExtensionHostManager（父页面）
     ├─ 快照/事件同步（消息、设置、会话）
     ├─ RPC（能力校验）
     └─ 写回（消息编辑、世界书、变量）
```

### 4.1 壳的 DOM 契约（快照版本 ST 1.19.1）

- 必须有：`#chat`、`.mes[mesid]`、`.mes_block`、`.mes_text`、`.mes_buttons`、`.avatar`；
- 设置：`#extensions_settings`、`#extensions_settings2`（可折叠块）；
- 菜单：`#extensionsMenu` + `#extensionsMenuButton`；
- 输入：`#send_textarea`、`#send_form`、`#leftSendForm`、`#rightSendForm`；
- 弹层：`#popup_container`、`.popup`；
- 顶栏按钮：`#top-settings-holder` 可提供空壳，避免 `null` 崩溃。

### 4.2 消息镜像

- 父页面按 ST 形状生成 `.mes` 节点：
  - `mesid` = 消息下标；`is_user` / `is_system` / `is_hidden` 类名；
  - `data-*` 与 `name` / `chid` 属性；
  - 头像、时间戳、swipe 指示器（最小）。
- 事件：新消息/编辑/删除/切换分支 → 发送快照增量，壳重绘对应节点（morphdom）；
- 扩展注入的按钮保留（按扩展命名空间标记，重绘时不覆盖）；
- 可选“DOM 写回”：扩展修改 `.mes_text` 后，点击保存/自动 debounce → 宿主更新消息正文（默认关闭，需能力 `chat.write`）。

### 4.3 设置 UI

- 壳内 `#extensions_settings` 渲染扩展面板；
- 父页面用抽屉打开壳，或把壳内设置节点通过 `postMessage` 尺寸自适应显示；
- 面板输入持久化仍走 `extension_settings` → 宿主 settings.save；
- 不把扩展 HTML 搬到 React 里执行。

### 4.4 输入与发送

- 壳内输入框与 FlyAI 输入框双向同步；`/slash` 统一走宿主命令表；
- 扩展调用 `send_message`/`Generate` 时走 L1 RPC；
- 避免双发送：以主机输入框为唯一提交入口，壳内发送按钮转发。

## 5. 分阶段实施

### P0：壳与加载验证（2 周）

- 新建 `extension shell iframe`（独立 srcdoc，CSP 同 L1）；
- ST-like DOM 骨架 + 基础 CSS（自写，不复制 ST CSS）；
- 消息镜像只读渲染；扩展入口加载 + activate hook；
- 验收：`token-counter`（设置+显示）、`quick-reply`（菜单+slash）可加载不崩；
- 产出：spike 报告、DOM 契约文档、截图。

### P1：设置/菜单兼容（3 周）

- `#extensions_settings`/`2` 抽屉、折叠、表单控件样式；
- `#extensionsMenu` 菜单弹出；
- 扩展设置持久化、`renderExtensionTemplateAsync` 读模板；
- 兼容库：jQuery、Popper、DOMPurify、morphdom、Fuse、hljs（按需 vendor）；
- 验收：translate/vectors/memory 的设置面板可操作（网络/生成依赖宿主能力）。

### P2：消息区注入（3 周）

- `.mes` 按钮/徽标/图片注入、点击 RPC、重绘保留；
- `MESSAGE_RECEIVED` 等事件与 DOM 同步；
- 可选 DOM 写回（能力门控）；
- 验收：tts 按钮、翻译按钮、caption 徽标、gallery 缩略图（只读）。

### P3：兼容视图（4–6 周，可选）

- 会话完全用壳渲染（FlyAI 主消息列表隐藏），支持扩展改写消息 HTML；
- 滚动/分支/swipe/编辑在壳内闭环；
- 仅对“必须聊天区渲染”的插件开启（expressions、gallery 全屏）；
- 风险最高，默认关闭。

总计：P0–P2 约 8 周；P3 再加 1–1.5 个月。

## 6. 安全

- 壳仍是 `sandbox="allow-scripts"` 的 opaque origin，无 `allow-same-origin`；
- CSP：`connect-src 'none'`，脚本只允许自身/内联/data；禁止远程 import；
- 网络：`net.fetch` + `st_net` 总开关 + manifest 白名单；Cookie/Authorization 丢弃；
- 密钥：只读状态，不提供明文；
- DOM 写回、消息发送、世界书写入等能力必须 manifest 声明 + 用户启用；
- 扩展之间不共享 DOM 命名空间；卸载即销毁 iframe；
- 第三方库只 vendor 许可证兼容的版本（MIT/BSD/Apache），并记录来源。

## 7. 许可与法务

- SillyTavern 为 **AGPL-3.0**：
  - 直接复制其 CSS/JS 到 FlyAI 并在网络分发，需要按 AGPL 提供对应源码；
  - **推荐自写** ST 形状 DOM 与基础样式（选择器/类名可兼容，样式实现原创）；
  - 第三方库（jQuery/MIT、Popper/MIT、DOMPurify/Apache-2.0、morphdom/MIT、Fuse/Apache-2.0、hljs/BSD）可直接 vendor。
- 不内置具体第三方扩展；安装时展示来源/许可证与“兼容模式”风险提示。

## 8. 兼容预期（保守）

| UI 类型 | 预期可用率 | 说明 |
|---|---:|---|
| 纯设置面板 | ~80% | 容器/表单/模板兼容后 |
| 菜单 + 简单弹层 | ~60% | 定位与抽屉差异 |
| 消息按钮/徽标 | ~60% | 镜像 DOM + 点击桥 |
| 聊天区渲染改写 | ~30–40% | 需 P3 兼容视图 |
| 拖拽/主题/布局类 | <10% | 不建议 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| ST DOM 版本漂移 | 扩展失效 | 固定 1.19.1 契约 + 兼容矩阵 + fixture 回归 |
| 双份消息渲染不同步 | 状态错乱 | 单一快照源 + 增量 morphdom + 事件版本号 |
| 扩展注入 DOM 被重绘覆盖 | UI 消失 | 按扩展命名空间标记，重绘保留节点 |
| CSS 冲突 | 视觉错乱 | 壳内独立文档、基础样式最小化；不继承父页面 CSS |
| 移动端性能 | 卡顿/内存 | 默认关闭 L3；按需创建；限制扩展数量与 DOM 大小 |
| AGPL 传染 | 法务 | 自写样式/不复制 ST 源码；vendor 库记录许可 |
| 供应链风险 | 远程代码 | 管理员安装 + 扫描 + 能力声明 + 网络代理 |

## 10. 配置与回滚

```python
class ExtensionSettings(BaseModel):
    ...
    l3_enabled: bool = False            # ST 兼容壳总开关
    l3_min_level: int = 256             # 谁能开启兼容模式
    l3_allow_dom_writeback: bool = False
```

- 默认关闭；开启后仍需单扩展手动“启用兼容模式”；
- 扫描为 L3 的扩展在列表中显示“需要兼容壳”，未开启时不可启用；
- 回滚：关闭 `l3_enabled` 即恢复 L1/L2 行为；壳 iframe 全部销毁，不影响主界面。

## 12. 测试方案

- 壳 fixture：
  - `ui-settings`：向 `#extensions_settings` 插入表单并读写 settings；
  - `ui-menu`：`#extensionsMenu` 弹层按钮；
  - `ui-message`：`.mes` 注入按钮，点击回调变量；
  - `ui-writeback`：修改 `.mes_text` 并写回（能力门控）；
- 事件/重绘回归：新消息/编辑/删除后，扩展注入节点仍在；
- 安全：`parent.document`、`localStorage`、外网 fetch 必须失败；
- 移动端：WebView/APK 内的滚动、软键盘、内存基线；
- 兼容矩阵：每个真实扩展一行（版本/等级/已用 UI 面/缺口/结果）。

## 13. 建议决策

1. 先做 **P1 设置/菜单**（收益最高、风险最低），再决定 P2；
2. P3 兼容视图只对少数高价值扩展开启，不做默认；
3. 不内嵌 ST 前端、不复制 ST CSS，避免 AGPL 与维护双份 UI；
4. 保持 L1/L2 为默认路径，L3 是“兼容模式”而非默认能力。

> 若目标是“尽可能兼容现有酒馆 UI 插件”，A 方案的 P1+P2 是性价比最高的组合；
> 若目标是“100% 还原 ST 体验”，则等价于重做 ST 前端，不建议。
